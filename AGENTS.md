# Nanotype: working rules for agents and people

(`CLAUDE.md` points here.)

A private writing app that keeps the text in the browser. **Read `PRINCIPLES.md` first**: it is the north star, and every change is judged against it (minimal, nothing distracts, private, never lose data, fewer clicks, transparency, clear to a first-time visitor, works everywhere, ask first what if we did not build it, a hammer not a jet engine, the simplest and lightest solution, the right part for each job, known patterns, creativity where there are none). Then `DESIGN.md` before changing the interface; `DEPLOY.md` for hosting.

## Working rules

- Commit locally as you go; push only when the user says "push". A push to `main` deploys to production at nanotype.app (and the old addresses).
- **Before every push, update `CHANGELOG.md`**: under today's date (newest day first), add one short bullet per change a person using the app would notice, in plain words, no commit hashes. Commits alone do not go in; every push does. If the day's heading exists, add to it. Include the changelog edit in the push.
- Never lose anyone's text: nothing is deleted or overwritten except by the person, on purpose. Storage keys (`zen.docs`, `zen.doc.<id>`, settings) are a contract with every browser out there; the document keys are in `src/js/keys.js` and nothing else names them; the settings are read and written in one place in `ui.js` (`loadState`/`saveState`) and listed in `keys.SETTINGS` for the backup. Do not rename them (a migration is the only way, and it reads the old names forever).
- The interface is split by part (`src/js/components/`: `ui.js` for init, settings, the menu and keyboard tables; `picker.js`, `docs.js`, `caret.js`, `lines.js`, `paste.js`, `sharing.js`, `files.js`, `contents.js`, `counter.js`, `key-sounds.js`, `ripples.js`); the stores (`documents`, `editor`, `backup`, `folder`, `move`) and the pure modules (`share`, `markdown`, `tidy`, `sounds`, `utils`, `stats`) are imported directly; what the interface parts share (elements, state, status, the picker) goes through `app.js`, never by one part reaching into another's internals. A new feature goes into the part it belongs to, or a new file of the same shape.
- Keep it simple: the smallest robust change that will last (`PRINCIPLES.md` 9–12). No frameworks, managers or abstractions for one use. Measure before optimising (see the figures in `DESIGN.md`).
- **Keys (the dialog in `public/index.html`, `.help-modal`) must always match the code.** It is a hand-written table; nothing generates it. Whenever a shortcut, a command name or a menu row changes or is added (`onDocumentKeyDown` and `commandItems` in `src/js/components/ui.js`, the `data-keys` on the column), update the Keys table in the same commit: the row's wording, its key, its group (Documents, Document, Editor, Appearance, Editing, Markdown: the menu's groups, then the editing keys). Before a push, read the table once against `onDocumentKeyDown` and the menu. The About line "Every command has a key. ⌘K lists them." depends on it.
- Analytics (`src/js/components/stats.js`, principle 15): one HTTP call per page view and per command, nothing else, and nothing personal, only how the product is used. Never add the PostHog SDK, autocapture, session recording, or any property that could carry text or identify a person; the address goes without its fragment. Whatever is sent must match the sentence in About; every field is listed in `docs/analytics.md`, and a new field goes on that list first.
- Never run `npm run build` while the dev server is up; it wipes `dist`. The dev server is `npm run dev` on port 3002.
- Sounds behave differently on the dev server (identical code sounded wrong on localhost:3002 and right on nanotype.app, 2026-10-06; Browsersync's injected script is the suspect). Judge audio on the live site.
- Facts about the product (name, former name, description, publisher, what leaves the browser, the lists) live in `src/facts.mjs`; the page's title, description, canonical, Open Graph and JSON-LD, the manifest and About must say the same (`test/seo.test.mjs` checks), and `robots.txt`, `sitemap.xml`, `llms.txt`, `llms-full.txt` are generated from it at build (`src/seo.mjs`), never edited by hand. Nothing is loaded by the app; the service worker caches none of them.
- `docs/` is public and ships with the repo. `docs/internal/` is gitignored: plans, launch notes and anything else not meant to be published go there, never in `docs/`.
- Tests: `npm test` for the share, markdown, names, tidy and seo modules (37 tests); `npm run test:browser` for the sixteen headless-Chrome suites in `test/browser/` (needs `npm run dev` on :3002; about four minutes). Run both before every push, and add a suite or a check when a behaviour is added or changed. The runner blocks `/stats/` in every test browser; never let an automated browser, script or curl loop reach the live site's counts in any other way (a suite run against nanotype.app counted 121 visitors in an hour on 2026-10-09). Test against the dev server; the live site is for a look by hand.
